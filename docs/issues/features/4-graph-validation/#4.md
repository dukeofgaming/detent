# 4 - Graph Validation
<!-- GitHub Issue #4 -->

## Description

`Graph` is now owned by the `graph_validation` feature slice. On the current `#3` branch, that slice remains additive and isolated; `compile` and `validate` stay structural-only until `#4` is layered back on.

The BPMN 2.0 XSD does **not** provide these semantic checks:

- `process` must have at least one `startEvent` (XSD uses `minOccurs="0"`)
- `process` must have at least one `endEvent` (XSD uses `minOccurs="0"`)
- All `sequenceFlow.sourceRef`/`targetRef` must point to real nodes (XSD uses `xsd:IDREF` but `quick-xml` does not enforce ID constraints)
- Graph connectivity, reachability, orphans, dead ends

These are Domain-layer semantic rules that belong in `Graph::validate()` and must be wired into both the `compile` and `validate` production paths.

## Notes
<!-- GitHub Section:Notes:4  -->

### Architecture — Clean Architecture layer assignment (2026-04-01)

1. **2026-04-01**: Confirmed that graph invariants belong in the **Domain layer**, not in the BPMN adapter or infrastructure.
    1. ADR-7 (Clean Architecture boundaries for workflow standards) was written and establishes four layers: Domain, Application, Adapter, Infrastructure.
    2. Graph checks are standard-neutral semantic rules — they apply regardless of whether the source was BPMN XML, MDX, SWS, or any future standard.
    3. The three-layer validation pipeline in the `validate` command is now: ① Adapter/Infrastructure (XSD schema, standard-specific) → ② Domain (`Graph::validate()`, standard-neutral) → ③ Application (orchestration, error mapping, CLI output).
    4. Phases 2 and 3 of this plan are therefore not just completing existing code — they are placing Domain semantics where they architecturally belong.

### Architecture — What full XSD validation can and cannot replace (2026-04-01)

1. **2026-04-01**: Full BPMN XSD validation was confirmed as a hard requirement. Evaluated whether it obsoletes any of this feature's scope.
    1. XSD **can** replace: XML element/attribute shape checks, namespace conformance, cardinality constraints already expressed in the schema.
    2. XSD **cannot** replace anything in this feature: start event and end event presence use `minOccurs="0"` in the BPMN XSD; `xsd:IDREF` for `sourceRef`/`targetRef` is not enforced by `quick-xml`; reachability, orphan detection, duplicate IDs, and gateway invariants are all engine-specific rules absent from the schema.
    3. All four phases of the plan remain necessary even after full XSD validation is enabled.

### Architecture — Multi-standard path implication (2026-04-01)

1. **2026-04-01**: Confirmed that detent will treat BPMN as the first standard adapter, with SWS and potentially others to follow.
    1. The graph invariants being implemented should eventually be expressed against a standard-neutral IR, not raw BPMN `Process` types.
    2. If `Graph` remains coupled to `Process` (BPMN-specific), plan a future migration to the neutral IR when ADR-7 alignment work begins.
    3. The current phased plan is still the right priority — the neutral IR does not exist yet, and wiring graph validation into `compile`/`validate` now is the correct incremental step.

### Test architecture — slice-owned integration target (2026-06-01)

1. **2026-06-01**: The `graph_validation` test suite was moved out of the
   library test target while staying inside the slice.
    1. Removed `#[cfg(test)] mod tests;` from `src/features/graph_validation.rs`.
    2. Kept the real tests in `src/features/graph_validation/tests/integration.rs`.
    3. Exposed the slice tests through the stable root harness file
       `tests/feature_slices.rs` instead of per-slice `Cargo.toml` entries.
    4. This keeps the slice test-owned and discoverable without making
       `cargo test --lib` run graph validation tests.
    5. Captured as ADR-10, which supersedes ADR-9 for test discovery.
    6. Verified with `cargo test --lib` and full `cargo test`.
