### Decision Point: XSD → YAML Validation Strategy

**Challenge:** XSD validates XML. We want to validate YAML frontmatter. Options:

1. **XSD → JSON Schema conversion** (then validate JSON representation of YAML)
   - Tools: `xsd2json`, Python `xmlschema`, etc.
   - Pros: JSON Schema is well-supported, can validate YAML-as-JSON
   - Cons: Lossy conversion, XSD features may not map 1:1

2. **XSD → Rust types generation** (then use serde for validation)
   - Tools: `xsd-parser-rs`, `yaserde`, or `quick-xml` with derive
   - Pros: Compile-time type safety, WASM-compatible
   - Cons: May need custom serde for YAML frontmatter format

3. **Hybrid approach**
   - Generate Rust types from XSD for the core BPMN model
   - Use those types for both XML and YAML (de)serialization
   - Validate compiled BPMN XML against XSD directly

**Leaning toward:** Option 3 (Hybrid) because:
- Rust types give compile-time safety
- Same types work for both XML and YAML via serde
- Can still validate final BPMN XML output against XSD
- Best WASM performance

3. Create ADR documenting the decision

### Experiment 2: XSD-to-Rust Type Generation with xsd-parser (2026-01-20)

**Attempt:** Use `xsd-parser` v1.4.0 to generate Rust types from BPMN 2.0 XSDs.

**Configuration:**
```rust
let config = xsd_parser::Config::default()
    .with_schema(Schema::File("src/assets/schemas/BPMN20.xsd".into()))
    .with_quick_xml_serialize()
    .with_quick_xml_deserialize();
```

**Result:** ❌ FAILED

The generated code has compilation errors:
- Duplicate type definitions (e.g., `TSubProcessType` defined multiple times)
- Unresolved imports
- Type conflicts from complex XSD inheritance

**Root cause:** BPMN 2.0 XSD is extremely complex with:
- Multiple namespace imports (BPMNDI, DI, DC, Semantic)
- Extensive type inheritance and substitution groups
- Many abstract types with multiple concrete implementations

**Conclusion:** 
The `xsd-parser` crate works well for simpler XSDs but struggles with OMG's 
complex multi-namespace BPMN schema. We need an alternative approach.

---

### Experiment 3: Handcrafted Types with Serde (Pivot)

**New approach:** Define minimal Rust types manually that cover the BPMN 2.0 
subset we need (as defined in spec.md), using `quick-xml` + `serde` for 
(de)serialization.

**Rationale:**
1. The spec only requires a subset of BPMN 2.0:
   - StartEvent, EndEvent
   - ServiceTask, ScriptTask
   - ExclusiveGateway, ParallelGateway
   - SequenceFlow
   - Process, Definitions
2. We can validate against XSD at test-time using an external validator
3. Manual types give us full control over YAML serialization

**Trade-offs:**
- ✅ Compile immediately, no build-time codegen
- ✅ Tailored exactly to our needs
- ✅ WASM-compatible
- ❌ Need to update manually if XSD changes (rare for BPMN 2.0)
- ❌ Risk of drift from XSD (mitigated by XSD validation tests)

**Result:** ✅ SUCCESS

Successfully parsed hello-world.bpmn2:
```
Definitions ID: _LvBOwNfUED6W5vyiHBWrAg
Process ID: hello_world
Start events: 1
End events: 1
Tasks: 1
Sequence flows: 2
```

The handcrafted types work with real-world BPMN files from jBPM Process Modeler.

### Experiment 5: XSD Runtime Validation with libxml (2026-03-26)

**Goal:** Leverage the bundled XSDs at `src/assets/schemas/` for runtime BPMN validation, fulfilling the original intent of ADR-001 (XSD as source of truth).

**Problem:** `parse_bpmn()` only used `quick-xml` deserialization—structurally invalid XML could pass as long as serde didn't error. No XSD schema validation existed anywhere in the pipeline.

**Technology evaluation:**

| Crate | Version | Verdict |
|-------|---------|---------|
| `xmlschema` | 0.0.1 | ❌ No public `validate()` API at all |
| `xsd` | 0.2.2 | ❌ Stub crate, not functional |
| `libxml` | 0.3.8 | ✅ Mature Rust bindings to libxml2 C library |

**Design decision:** Feature-flag `xsd-validation = ["libxml"]` so:
- Default builds remain pure-Rust and WASM-compatible
- Environments with `libxml2-dev` installed can opt in to full XSD validation
- The WASM path stays open; XSD validation just won't be available there

**Implementation:**
- `src/bpmn/xsd_validator.rs` — new module, only compiled with `xsd-validation` feature
  - `validate_bpmn_xsd(&str)` — validates an XML string against `BPMN20.xsd`
  - `validate_bpmn_file_xsd(&Path)` — validates a file path directly
  - `XsdValidationError` enum with `FileReadError`, `XmlParseError`, `SchemaParseError`, `ValidationError` variants
  - Schema path embedded at compile time via `env!("CARGO_MANIFEST_DIR")`
- `src/commands/validate.rs` — refactored to 3-step pipeline: ① XSD (feature-gated) → ② serde parse → ③ semantic checks
- `src/bpmn.rs` — conditional `pub mod xsd_validator` and re-exports
- `Cargo.toml` — `[features]` block + optional `libxml` dep
- `.devcontainer/Dockerfile` — added `libxml2-dev` + `libclang-dev` for devcontainer rebuild

**Result:** ✅ SUCCESS (structural)
- Default build (`cargo test`): all 29 tests pass
- `--features xsd-validation` build: blocked pending devcontainer rebuild (libxml2-dev not installed; sudo blocked by "no new privileges" security flag in current container)
- ADR-001 updated with full rationale; README updated with feature docs

### 2026-06-01: Slice-owned integration targets instead of lib-wired tests

**Hypothesis:**

library test target because each slice root declared `#[cfg(test)] mod tests;`.

binary target was not provisioned for the library test run.

**Changes Made:**

1. **Slice tests moved out of the library target:**
   - Removed `#[cfg(test)] mod tests;` from

   - Removed the crate-level smoke test from `src/features/mod.rs`

2. **Slice-local integration test target introduced:**
   - Added `[[test]]` entry `convert_bpmn_to_mdx_slice_tests` in `Cargo.toml`
   - Registered path:
     `src/features/convert_bpmn_to_mdx/tests/integration.rs`

3. **Feature #3 tests kept slice-owned but no longer lib tests:**
   - Moved all former `tests/mod.rs` coverage into
     `tests/integration.rs`

     `src/features/convert_bpmn_to_mdx/tests/assets/hello_world/`
   - Kept CLI command coverage with `assert_cmd` inside the slice test target

4. **Documentation updated to match the new rule:**
   - ADR-9 was added, then superseded by ADR-10 for test discovery
   - `src/AGENTS.md` updated to forbid wiring slice tests into library modules

**Validation:**

1. `cargo test --lib` now runs `0` tests and succeeds, which confirms the

**Follow-up adjustment:**

The intermediate ADR-9 approach used one `[[test]]` entry per slice in
`Cargo.toml`. That was replaced by ADR-10 because adding new tests should not
require repeated TOML edits. The final layout keeps the real test code in the
slice, but exposes it to Cargo through a stable root harness file:

- `tests/feature_slices.rs`

### 2026-06-02: Clean Architecture audit — layer boundary corrections

**Context:**

Both vertical slices (`convert_bpmn_to_mdx`, `graph_validation`) use the four-layer
folder layout (domain / use_cases / adapters / infrastructure), but dependency
direction does not yet match ADR-7. The slices are layered by name, not by rule.

**Findings validated with the developer:**

1. **Domain must not depend on adapters.**
   `convert_bpmn_to_mdx/domain.rs` currently re-exports `adapters::bpmn::*` and
   `adapters::mdx::*`. That inverts the dependency arrow. Domain should own
   standard-neutral workflow semantics; adapter types are an outer concern.

2. **BPMN types do not belong in domain.**
   `graph_validation/domain/bpmn/` duplicates handcrafted BPMN structs that
   already live in `convert_bpmn_to_mdx/adapters/bpmn/types/`. Per ADR-7, domain
   should expose a standard-neutral IR (`Workflow`, `Node`, `Edge`, graph
   invariants). BPMN element names (`StartEvent`, `ExclusiveGateway`) belong in
   the BPMN adapter layer only.

3. **XSD validation belongs in infrastructure.**
   `xsd_validator.rs` currently lives under `adapters/bpmn/` and calls libxml
   directly. ADR-7 places libxml behind a `SchemaValidator` port implemented in
   infrastructure. Adapters translate formats; infrastructure wraps host libraries.

4. **Cross-slice coupling at the wrong layer.**
   `graph_validation` use cases import `convert_bpmn_to_mdx::adapters::bpmn`
   directly and map adapter types into a second copy via `to_domain_process`.
   The correct flow is: adapter parses BPMN XML → maps to shared domain
   `Workflow` → domain `Graph` validates invariants.

5. **CLI orchestration is split and incomplete.**
   `main.rs` wires only `convert_bpmn_to_mdx/infrastructure/cli`, which skips
   graph validation. A parallel CLI exists under `graph_validation/infrastructure/cli`
   but is not connected. Validation orchestration should live in use cases; CLI
   handlers should remain thin IO wrappers.

**Decisions:**

| Concern | Current (wrong) | Target (ADR-7) |
|---------|-----------------|----------------|
| BPMN serde types | adapter + duplicated "domain/bpmn" | adapter only |
| Compile/import IR | adapter `Definitions` | adapter `Definitions` → domain `Workflow` at boundary |
| Graph validation | domain on BPMN-shaped copy | domain on standard-neutral `Workflow` |
| XSD / libxml | `adapters/bpmn/xsd_validator.rs` | `infrastructure/` behind `SchemaValidator` port |
| `domain.rs` | re-exports adapters | real domain types + invariants |

**ADR-2 clarification:**

The shared compile/import IR remains the handcrafted BPMN adapter types (ADR-4).
That IR is **not** the domain model. Graph semantics and future multi-standard
support require a separate standard-neutral domain layer that adapters normalize
into.

**Vertical slices remain valid:** [[ADR-7]] does not require abandoning feature
slices. Each slice keeps domain / use_cases / adapters / infrastructure folders,
but dependency direction must point inward. Slices may share a common domain
module rather than reaching into each other's adapter layers.

**ADR-2 implementation notes:**

The compile/import IR is an **adapter-layer** concern, not the domain model.
Per [[ADR-7]], graph invariants, reachability, and execution semantics belong
in a standard-neutral domain `Workflow` type. Adapters translate between BPMN
XML/MDX and that domain model at the boundary.

Observed anti-patterns to avoid:

1. Re-exporting adapter types from `domain/` (inverts dependency direction)
2. Duplicating BPMN structs under `domain/bpmn/` in a second slice
3. Running graph validation directly on adapter types instead of normalized
   domain IR

The intended data flow for validation is:

```
BPMN XML → adapter parse → adapter BPMN types → adapter map → domain Workflow → domain validate
MDX      → adapter parse → adapter BPMN types → adapter map → domain Workflow → domain validate
```

**ADR-3 implementation notes:**

Runtime XSD validation is an infrastructure concern. Default and WASM builds
stay pure Rust (`quick-xml` + `serde`); native builds may opt into libxml via
the `xsd-validation` feature. Adapters must not call libxml directly.

**ADR-4 implementation notes:**

**Layer placement:** Handcrafted BPMN types are adapter concerns. They carry
serde/quick-xml attributes for XML and YAML interchange. Domain code must not
import or duplicate them; adapters map into a standard-neutral domain IR
([[ADR-7]]) when semantic validation or execution is required.

**XSD validation placement:** Runtime XSD checks (via libxml or `xmllint`) are
not part of the handcrafted type definitions. They belong in **infrastructure**
behind a `SchemaValidator` port ([[ADR-7]]), feature-gated for native builds
(`xsd-validation`) so default/WASM targets remain pure Rust. Adapters parse and
translate; infrastructure wraps schema-validation libraries.

**Observed anti-pattern:** Placing `xsd_validator.rs` under `adapters/bpmn/` and
re-exporting adapter types from `domain/` couples outer layers incorrectly and
creates duplicate BPMN struct copies across slices. Both should be refactored
toward adapter → domain mapping with infrastructure-owned schema validation.

**Next steps:**

All Clean Architecture Alignment acceptance criteria are now complete. Future
refactoring should focus on: extracting shared `Workflow` type when a third
slice joins; formalizing the `SchemaValidator` port into its own module if
additional validator backends are needed; and migrating the `convert_bpmn_to_mdx`
CLI validate handler to the composed `ValidateWorkflow` pipeline when it needs
graph validation.
