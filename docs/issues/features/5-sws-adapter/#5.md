# 5 - Serverless Workflow (SWS) Standard Adapter
<!-- GitHub Issue #5 -->

## Description

Detent currently supports BPMN 2.0 as its first standard adapter (via `compiler/bpmn/`). ADR-7 explicitly reserves a future SWS adapter slot and establishes the architectural boundary for multi-standard support. Issue #4 confirms SWS is the next standard to integrate.

The **Serverless Workflow** specification is a CNCF sandbox project at v1.0.3 that defines a JSON/YAML DSL for workflow definitions. An official Rust SDK exists at `github.com/serverlessworkflow/sdk-rust` (v1.0.0-alpha6.3) with three crates: `serverless-workflow-core` (DSL models), `serverless-workflow-builders` (programmatic construction), `serverless-workflow-io` (read/write JSON/YAML).

### What needs to be built

A new SWS adapter at `compiler/sws/` that mirrors the BPMN adapter structure:

1. **Parser** — Read SWS JSON/YAML into the SDK's core types (or handcrafted types if the SDK is insufficient)
2. **Normalizer** — Convert SWS types into the domain IR (`Workflow`, `Graph`, etc.)
3. **Serializer** — Convert domain IR back into SWS JSON/YAML
4. **Validation** — Integrate SWS schema validation into the `validate` command pipeline
5. **Compilation** — Wire SWS parsing into `compile` so MDX can import SWS workflows

### Constraints

- Follow the same Clean Architecture pattern as `compiler/bpmn/`: parse → normalize → domain IR
- The SWS Rust SDK is pre-1.0 (alpha); decisions need to be made about depending on it vs. handcrafting types
- `serde_json` and `serde_yaml` are already workspace dependencies, so serialization plumbing is available
- SWS uses a fundamentally different workflow model (action-based, event-driven) vs. BPMN (flow-chart with gateways), so the normalizer must handle semantic translation carefully

### Out of scope (for this issue)

- Full event-driven execution of an SWS workflow (the engine doesn't support that yet)
- SWS function/event/service binding execution
- Sub-workflow / workflow composition

## Notes
<!-- GitHub Section:Notes:5  -->

### Architecture — Layer assignment (2026-05-07)

1. **2026-05-07**: Confirmed SWS adapter belongs in the **Adapter** layer per ADR-7, mirroring the BPMN adapter.
    1. SWS parsing and schema validation: Adapter/Infrastructure
    2. SWS → domain IR normalization: Adapter (Translator/Mapper pattern)
    3. Domain IR → workflow semantics: Domain (reuses existing `Graph::validate()`, execution rules)
    4. Orchestration (import, validate, compile): Application

### Architecture — SDK dependency risk (2026-05-07)

1. **2026-05-07**: The `serverless-workflow-sdk-rust` is at v1.0.0-alpha6.3. Key evaluation criteria:
    1. Are the core model types complete for the v1.0.3 spec?
    2. Do they serialize/deserialize correctly with serde?
    3. Is the crate actively maintained (last release Jan 2025)?
    4. Does the IO crate handle both JSON and YAML?
    - If the SDK is insufficient, handcraft a minimal subset of types in `compiler/sws/types/`.

### Architecture — BPMN vs SWS semantic gap (2026-05-07)

1. **2026-05-07**: SWS and BPMN have fundamentally different workflow models:
    1. BPMN is flow-chart oriented: `sequenceFlow` connects `startEvent` → `task` → `gateway` → `endEvent`
    2. SWS is action/state oriented: a `State` has `actions[]` and `transition`/`end`, with event-driven, parallel, and callback state types
    3. The normalizer must translate SWS states into the graph IR without losing semantic information
    4. Some SWS concepts (event triggers, function definitions, retry policies) have no BPMN equivalent — these may need to be stored as extensions on the domain IR
