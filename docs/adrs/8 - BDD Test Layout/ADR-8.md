## Context

Slice-owned tests follow the discovery model established by [[ADR-6]] (stable root
harness, generated by `build.rs`). BDD is the **style** for all slice tests — not
a separate test type. Tests are grouped by **level** (unit, functional,
integration, e2e) while sharing one Cucumber World per slice.

We needed a layout that:

- makes the test-level hierarchy visible at a glance
- separates shared steps from scenario-local steps
- scales to many scenarios without a single large file
- respects screaming architecture ([[ADR-7]]): directory and file names should
  reveal content

## Decision

Adopt the following layout under `src/features/<slice>/tests/`:

```
tests/
├── world.rs                 # Cucumber World struct + run() entrypoint
├── steps/                   # slice-wide shared step definitions
│   ├── mod.rs
│   ├── given.rs
│   ├── when.rs
│   ├── then.rs
│   └── and.rs
├── unit/
│   ├── unit.feature
│   └── scenarios/
├── functional/
│   ├── functional.feature
│   └── scenarios/
├── integration/
│   ├── integration.feature
│   └── scenarios/
├── e2e/
│   ├── e2e.feature
│   └── scenarios/
└── assets/                  # fixtures (unchanged)
```

### Test level taxonomy

| Level | Scope |
|-------|-------|
| **unit** | Single type/function, no use-case orchestration |
| **functional** | Use-case / domain orchestration in-process |
| **integration** | Adapters + real artifacts (XML, XSD, fixture files) |
| **e2e** | CLI subprocess via `assert_cmd` |

### Options

1. **Flat `steps.rs` + flat scenario files**: Simple but grows without bound
2. **Level directories + `{level}.feature` + `scenarios/` + shared `steps/`**: Structured, screams intent — chosen
3. **Gherkin-only: no scenario `.rs` files**: All Cucumber, no Rust per scenario — inflexible
4. **Separate World per test level**: Duplicates step registration — rejected

### Rationale

1. **`world.rs` at `tests/` root.** One World struct and one `run()` per slice.
   `run()` points at the slice `tests/` directory; Cucumber discovers all
   `{level}/{level}.feature` files automatically.

2. **One feature file per test level.** Each level gets exactly one Gherkin file
   named after the level (`unit.feature`, `functional.feature`, etc.). BDD is
   not a test type — it is how every level is authored.

3. **Scenarios in `{level}/scenarios/`.** Each `.rs` file contains step
   definitions for one or a tight group of related Gherkin scenarios.

4. **Shared steps under `steps/given.rs`, `steps/when.rs`, `steps/then.rs`,
   `steps/and.rs`.** Step definitions shared across levels live in a file that
   matches the Gherkin keyword they implement.

5. **Scenario-local steps stay in the scenario file.** When a step is used by
   exactly one scenario group, it lives in `{level}/scenarios/<group>.rs`. When
   copied to a second scenario file, it graduates to shared `steps/`.

6. **Modules declared via `#[path = "..."]`.** Inside `world.rs`, scenario
   files are declared with `#[path]` attributes. The steps module uses
   `mod steps;` resolved to `steps/mod.rs`.

7. **`build.rs` discovers `tests/world.rs`.** The build script looks for
   `src/features/*/tests/world.rs` and emits one harness test per slice.

## Consequences

### Positive

1. **Level separation.** Unit, functional, integration, and e2e concerns are distinguished by directory.
2. **Unified BDD style.** All tests read as scenarios; no parallel plain-Rust test harness.
3. **Onboarding.** Contributors find scenarios by level and name in the directory tree.
4. **Screaming architecture.** Every directory name reveals its purpose.

### Negative

1. **More files.** Deeper tree than a flat layout. Mitigation: IDE navigation.
2. **Path resolution.** Steps use `use super::super::ConvertWorld` from `steps/*.rs`. Mitigation: confined to one import line per file.
3. **Empty `and.rs`.** Placeholder for shared "And" continuations; compiles cleanly when empty.
